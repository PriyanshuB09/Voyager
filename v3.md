# Voyager v3

## What changed, why I changed it, and how to use it

Voyager v3 started with a fairly simple goal: I wanted building an autonomous routine to feel less like editing a collection of files and more like working through an idea.

An autonomous routine is not only a path. It is the path, the decisions around it, the events that happen during it, the field obstacles, the robot's limits, and eventually the question that matters most: *is the real robot doing what I asked it to do?*

The releases from `v3.0.1-alpha` through `v3.3.2-alpha` gradually brought those pieces together. Some releases added large new tools. Others made the same tools calmer, faster, or more trustworthy. This guide explains the result from a driver's or programmer's point of view rather than going deep into the code behind it.

## The short version

Here is the general direction of each release:

| Version | Main idea |
| --- | --- |
| `v3.0.1-alpha` | Turn Voyager into a complete workspace instead of only a path editor |
| `v3.1.1-alpha` | Organize the growing collection of field tools without crowding the toolbar |
| `v3.1.3-alpha` | Make the path-planner controls behave the way their labels suggest |
| `v3.2.0-alpha` | Make the application substantially faster, calmer, and easier to scan |
| `v3.3.0-alpha` | Give live robot diagnostics their own workspace and make NT4 sources configurable |
| `v3.3.1-alpha` | Stabilize tab switching, saved work, keyboard use, and long-running telemetry |
| `v3.3.2-alpha` | Make live motion easier to understand visually and fix the floating tree's layer order |

## The early v3 foundation

### A workspace that remembers the whole project

Before v3, saving mostly meant exporting the files the robot needed. That is still important, but those files do not describe everything that makes an editing session useful. They do not naturally include where you placed the tree blocks, your field image, obstacle map, open path, interface preferences, or the history of changes that led to the current routine.

V3 added a separate Voyager workspace record alongside the robot files. It remembers the editor as an editor, not just as a file generator. This is why selecting a WPILib project now feels more like opening a project than choosing an output folder.

In the **Save** window, path export and workspace metadata are separate choices:

- **Save this path** updates only the path you are currently editing.
- **Save all paths** updates every path and the autonomous tree used by the robot.
- **Save metadata now** records the complete Voyager workspace.
- The two automatic-save options let you decide whether exported paths, workspace metadata, or both should stay synchronized while you work.
- **Publish selected auto on connect** is useful when you want the robot to receive the current routine as soon as the connection becomes available.

I separated these jobs because teams do not always want the same behavior. You may want frequent editor backups without constantly rewriting deploy files, or you may want every path edit exported immediately. V3 lets you choose.

### Version history that is actually useful during practice

V3 also introduced a visual version history. Saving creates checkpoints of the complete tree, paths, and obstacle map. Automatic saves can create checkpoints too.

The point is not to replace Git. It is to give you a quick recovery button inside the application. If a route looked better ten minutes ago, you can inspect the timeline and restore that state without trying to manually undo an entire practice session.

Use it like this:

1. Open **Tools → Version history**.
2. Look at the timestamp and the path, block, and waypoint counts.
3. Choose **Restore** on the checkpoint you want.
4. Review the restored routine before saving it over the project copy.

### Obstacles and generated paths

The obstacle map was one of the largest v3 additions. You can draw measured field obstacles, name them, move them visually, or enter their exact dimensions. Voyager then uses the configured robot size to leave room for the whole robot—not only its center point.

To use it:

1. Open **Tools → Obstacle map**.
2. Add an obstacle for each area the robot must avoid.
3. Resize and position the rectangles to match the real field.
4. Return to the Auto builder and select a path block.
5. Press **Plan path**.
6. Choose a starting point, or select an existing waypoint to keep the beginning of a path.
7. Choose the destination.

Voyager generates a route around the obstacle map, but the result is still an ordinary editable path. You can move waypoints, adjust headings, add events, or simplify it further. I wanted the planner to be a strong starting point, not a black box that takes control away from the user.

Two planner sliders control the character of the generated route:

- **Relative waypoint amount** changes how much detail the search can use.
- **Relative path sharpness** changes how willing the route is to make tighter direction changes.

`v3.1.3-alpha` corrected these sliders so **Very low** and **Very high** consistently mean what they say. If you used an earlier build and the endpoints seemed backward, that was a real bug rather than an unusual planner rule.

### Event Zones

An Event Zone gives a command a beginning and an end along a path. It is useful for actions that should stay active over a section of motion—for example, running an intake while crossing part of the field and stopping it afterward.

Add an **Event Zone**, drag its **S** and **E** handles to the desired positions, and enter the start and end event names. Voyager exports the zone as normal start and end events so the robot-side behavior remains straightforward.

### Mirroring and the More Tools menu

Alliance-side routines often begin as reflections of one another. V3 added **Mirror X** and **Mirror Y** so a selected path can be reflected without rebuilding it waypoint by waypoint. Headings are mirrored with the path, while events and constraint positions stay attached to their corresponding places along it.

As more field tools were added, the toolbar started becoming crowded. `v3.1.1-alpha` grouped mirroring and obstacle visibility under **More Tools**. This was a small release, but it established an important design rule for later versions: a feature should be easy to find without forcing every possible action onto the screen at once.

### A more flexible interface

The early v3 workspace became much more adaptable to different screens. Panels can be resized, field views preserve their scale, dialogs reflow on smaller windows, and the full-size Auto focus layout turns the path tree into a draggable and resizable floating window.

V3 also expanded appearance settings. Color themes and interface designs are separate, so you can choose the colors you like without being locked to one font, spacing system, or panel shape.

These options were not added only for decoration. Teams use Voyager on laptops, driver-station displays, shop monitors, and unusual window sizes. The interface needs to remain usable in all of them.

### A path tree that is harder to lose

V3 improved the tree itself as routines became larger. Connection lines choose the nearest side of each block, which keeps branches more readable when nodes are arranged above, below, or beside one another. Voyager also refuses a connection that would loop back into itself.

If you pan far away from the routine, **Nearest path** brings the closest path block back to the center. When Voyager cannot see any path blocks, it offers the same recovery action directly in the warning. I added this because an empty-looking tree should not make someone wonder whether their routine was deleted when it is only off-screen.

## v3.2: faster and calmer

By `v3.2.0-alpha`, Voyager could do much more, but that also made it easier for the application to feel busy. This release was a deliberate cleanup.

The interface moved toward a calmer PathPlanner-inspired look: larger system text, simpler graphite panels, softer accent colors, fewer glows, and less competing information. The title bar was reduced to the workspace controls, layout choices, **Save**, and one **Tools** menu. The Auto maker field became the visual priority.

The practical difference is that you should be able to answer these questions quickly:

- Which workspace am I in?
- Which path am I editing?
- Where are the tools for the job I am doing now?
- Is the project saved?

The release also made startup and interaction much faster. NetworkTables support waits until it is needed, dragging updates visually without repeatedly rebuilding the entire editor, and background saving waits for a sensible idle point. Live trails and activity history are bounded so a long session does not become slower simply because the application has been open for hours.

You do not need to configure any of these performance changes. The intended result is simply that Voyager opens sooner, dragging feels direct, and moving between parts of the application does not interrupt your train of thought.

## v3.3: Auto building and live diagnostics become separate jobs

### Two focused tabs

`v3.3.0-alpha` separated the application into **Auto builder** and **Live robot** tabs.

This change was about attention. While editing an autonomous routine, you need the field and path tree. While diagnosing the real robot, you need its connection, pose, NetworkTables sources, and motion comparison. Showing both jobs at the same time made each one harder to read.

Use **Auto builder** to create and edit. Use **Live robot** when the robot is connected and you want to understand what it is reporting.

### Choosing NetworkTables topics instead of assuming them

The Live robot sidebar can browse the complete hierarchy of topics announced by the NT4 server. Folders can be expanded, topics can be searched, and a topic path can still be typed manually.

Voyager keeps useful AdvantageKit defaults for:

```text
/AdvantageKit/DriverStation/DSAttached
/AdvantageKit/RealOutputs/Odometry/Robot
```

Those defaults are only starting points. If your logging layout or robot library publishes the same information somewhere else, choose the correct topic from the browser.

There are four source choices:

- **Driver Station attached** tells Voyager whether the robot should be treated as connected.
- **Odometry / Robot** supplies the live field pose.
- **Measured swerve ChassisSpeeds** is the motion the drivetrain is actually producing.
- **Setpoint swerve ChassisSpeeds** is the motion the drivetrain is being asked to produce.

The two ChassisSpeeds sources are optional. Live position works without them; they add motion comparison and diagnostic information.

Voyager accepts the normal WPILib ChassisSpeeds structure as well as simple number lists and JSON-style values. In practice, that means most teams can point the selector at the topic they already publish instead of creating a Voyager-specific duplicate.

### Direct NT4 and FRC Web Components modes

Some robot setups connected reliably through FRC Web Components while custom NT4 clients were less cooperative. Rather than forcing everyone onto one implementation, v3.3 added a switch between **Direct client** and **FRC Web Components**.

Both modes show the announced topic tree and listen only to the sources you select. If one mode does not behave correctly with your robot, switch to the other before changing the topic paths. This makes connection troubleshooting much less mysterious.

### Detecting possible slip or collision

When measured and setpoint ChassisSpeeds are selected, Voyager compares what the drivetrain was commanded to do with what it appears to be doing.

If the disagreement continues long enough to look meaningful, Voyager shows **Possible collision or wheel slip**. The robot perimeter and the affected part of the trail turn red. They return to normal only after the motion has recovered for a short period, which prevents the warning from flickering on and off because of one noisy packet.

This is a clue, not a verdict. A large disagreement can come from wheel slip, contact with another object, acceleration limits, a control problem, or inaccurate telemetry. The purpose is to point your attention at the moment when the real robot stopped matching the request.

### Reading the new motion arrows

`v3.3.2-alpha` made those ChassisSpeeds easier to understand without staring at numbers.

- **Cyan** represents measured motion.
- **Pink** represents the setpoint.
- A straight arrow combines `vx` and `vy` to show the direction and relative size of translation.
- A curved arrow shows rotation. Its direction shows which way the robot is turning, and a longer arc represents a larger `omega` command.
- The pink setpoint lines are dashed, so both sources remain visible when the two motions are almost identical.

The cards below the field use the same colors and show linear speed, `vx`, `vy`, and `omega` with units. A healthy robot will not make the two drawings perfectly identical every instant, but they should generally tell the same story.

For example, if the pink arrow points forward while the cyan arrow stays very short, the robot is being told to move but is barely moving. If the pink and cyan straight arrows match but their rotation arcs strongly disagree, the problem is more likely related to turning than translation.

### Cropping field images

Every new field image now opens a crop step. Drag the crop area until it contains the actual playable field and removes broadcast borders, labels, or empty padding. If the existing image needs another pass, use **Tools → Crop field image**.

This matters because every pose and waypoint is drawn against the configured field dimensions. Extra image borders make a mathematically correct position look visually wrong. Cropping gives the image and the meter coordinate system the same usable area. Voyager also reduces unnecessarily large uploads before storing them, keeping the workspace lighter without asking you to edit the image elsewhere first.

## The stabilization releases

Large workspace changes exposed a few bugs that only appeared after switching tabs or reopening saved projects. `v3.3.1-alpha` concentrated on those less glamorous but important details.

The most visible example was a partial white circle that could appear on the Auto field after visiting Live robot. It came from field overlays briefly using the previous field's size. The same issue could make Voyager claim that no path blocks were visible when they were clearly on screen. The fix makes the field and tree measure themselves again whenever the Auto workspace returns.

That release also:

- Clears temporary playback, planner, drag, and popup state when leaving Auto builder.
- Keeps the activity message to the right of the other navigation controls.
- Recovers invalid saved dimensions or duplicate internal IDs instead of allowing broken geometry onto the screen.
- Keeps waypoint handoff circles within sensible field bounds, even when an older saved value is invalid.
- Stops pending automatic-save work cleanly when automatic saving is disabled or its destination changes.
- Handles path filenames more safely on Windows and warns when two names would become the same file.
- Restores custom themes correctly.
- Improves keyboard access for tree blocks, waypoints, rotation targets, dividers, and dialogs.
- Clears stale NT4 topics and old speed samples after disconnects or transport changes.
- Makes dialogs, file access, and application navigation more defensive.

`v3.3.2-alpha` then fixed one final focus-layout problem: the floating path-tree window could slide underneath the Auto maker toolbar. It now stays above the field controls while remaining below the application's main navigation and dialogs.

## A practical first session in v3

If you are opening v3 for the first time, this is the order I recommend:

1. Open **Tools → Settings** and select the WPILib project.
2. Upload and crop the field image, then enter the real field dimensions and origin corner.
3. Enter the robot dimensions, center of rotation, and swerve-module placement.
4. Set the motion limits, tolerances, controller values, and planner preferences.
5. Build the routine structure in the path tree before trying to perfect every path.
6. Open each path block and add waypoints, rotation targets, events, Event Zones, and constraint zones.
7. If the field has important obstacles, map them and use **Plan path** as a starting point.
8. Use **Playback** to check direction, timing, events, rotation, and swerve behavior.
9. Save the workspace metadata and export all paths to the robot project.
10. Switch to **Live robot**, connect to NT4, and verify the DS and odometry sources.
11. Optionally choose measured and setpoint ChassisSpeeds to enable motion arrows and slip/collision hints.
12. Select the intended routine in the tree and publish it when the robot is ready.

The important habit is to move between planning and evidence. Build the routine in Auto builder, preview it, run it, and then use Live robot to compare the real result with the intent.

## What v3 is trying to be

V3 does not try to hide autonomous programming behind one giant **Generate** button. It tries to make the important parts visible: the sequence, the geometry, the timing, the robot's limits, and the live result.

The path planner is there when drawing everything manually is wasteful. Manual editing is still there when the generated route needs judgment. The live warning is there to focus your attention, not to replace log review. Themes and layouts are flexible, but the working field remains the center of the application.

That balance is the main idea behind the whole v3 series: make Voyager powerful enough for a complicated autonomous routine, but calm enough that you can still understand what the robot is supposed to do.
